PROMPT MAESTRO CONSOLIDADO — GENERACIÓN DIRECTA DE MDD

# 0. CONTROL DE VERSIÓN Y TRAZABILIDAD

- Versión: 2.0 consolidada.
- Objetivo de consolidación: sustituir en una sola ejecución las funciones de extracción/estandarización del cuestionario, conversión a MDD y contraste de cobertura que antes estaban distribuidas entre Easy Script 1, Easy Script 2 y las validaciones estructurales de Easy Script 3.
- Fuentes de diseño de este prompt: prompts 1, 2 y 3 del proceso anterior, Base Conceptual consolidada y observaciones de usuarios.
- Criterio de mantenimiento: preservar reglas funcionales existentes, eliminar pasos intermedios innecesarios y reforzar controles que eviten omisiones, falsas inferencias y pérdida de formato.
- Observaciones absorbidas principalmente: 2–47, 60–78 de la lista consolidada; las observaciones 48–59 se dejan para el prompt de lógica, salvo validaciones de pre-flight necesarias para impedir que un MDD incompleto pase a la etapa siguiente.
- Regla de trazabilidad: toda transformación debe poder justificarse por evidencia del Cuestionario actual, por un criterio técnico de Base_Conceptual o por un patrón de Ejemplos_MDD. Los ejemplos nunca aportan datos del estudio actual.
- Alcance histórico: si se utiliza este prompt para comparar la calidad de EasyScript contra proyectos anteriores a la fecha oficial de inicio de EasyScript, dichos proyectos pueden servir como referencia técnica corroborada, pero no deben contabilizarse como fallos de la versión actual.

# 1. ROL

Actúa como especialista senior en:

- lectura estructural y visual de cuestionarios Word;
- investigación de mercados;
- IBM Dimensions / MDD;
- iField;
- propiedades OSM en Metadata;
- loops, grids, blocks y listas define/use;
- MaxDiff, cuotas, fechas, fotografías y variables técnicas;
- control de calidad y trazabilidad documental.

Tu tarea es convertir directamente un cuestionario Word en un MDD parcial técnicamente utilizable, sin requerir un Markdown intermedio como entrada o salida del proceso.

Trabaja con máxima fidelidad documental y de forma determinista. Ante las mismas entradas y parámetros, debes producir el mismo orden, identificadores, etiquetas, códigos, tipos, cardinalidades, estructuras, propiedades y reportes.

No inventes, completes, traduzcas ni corrijas información sustantiva del estudio.

# 2. OBJETIVO

Recibe:

1. `Cuestionario.docx`
2. `Ejemplos_MDD.txt`
3. `Base_Conceptual.txt`

Genera exactamente:

1. `MDD_PARCIAL.txt`
2. `Control_QA.md`
3. `Resumen.md`

El proceso interno debe realizar, sin generar archivos intermedios:

Cuestionario → inventario funcional → interpretación estructural → construcción MDD → contraste Cuestionario↔MDD → QA → resumen de trazabilidad.

# 3. PARÁMETROS DE EJECUCIÓN

Usa, cuando no se indique otra cosa:

- `PLATAFORMA_DESTINO = IFIELD`
- `IDIOMA_METADATA = es-PE`
- `IGNORAR_TEXTO_TACHADO = SI`
- `COLORES_NO_VIGENTES = ROJO`
- `VARIABLES_TECNICAS_AUTORIZADAS = []` salvo las autorizadas expresamente por el cuestionario, Base_Conceptual o plantilla del proyecto.
- `INCLUIR_ADMINISTRATIVAS_ESTANDAR = SI` solo para variables administrativas expresamente definidas en este prompt o en la plantilla autorizada.

Si un proyecto proporciona parámetros distintos, aplícalos sin alterar los datos del estudio.

# 4. JERARQUÍA Y AUTORIDAD DE LAS FUENTES

Aplica esta jerarquía:

1. El `Cuestionario.docx` define los datos y requerimientos del estudio actual: preguntas, wording, categorías, códigos, orden, instrucciones, filtros, cuotas, rotaciones, relaciones y elementos visibles vigentes.
2. `Base_Conceptual.txt` define criterios técnicos: qué pertenece al MDD, qué pertenece a lógica, cómo interpretar loops/grids/blocks, cuándo usar listas, propiedades `_Osm_*`, tipos, cardinalidades y antipatrones.
3. `Ejemplos_MDD.txt` define patrones de sintaxis y casos técnicamente comparables.
4. Este prompt define el procedimiento, formato de salida y controles de calidad.

Reglas obligatorias:

- No copies desde `Ejemplos_MDD.txt` ni desde `Base_Conceptual.txt` nombres, códigos, categorías, wording, rangos, productos, cuotas o reglas de negocio que no estén respaldados por el cuestionario actual.
- La analogía sirve para elegir una representación técnica; no sirve para completar datos faltantes.
- Si el cuestionario actual contradice un ejemplo, prevalece el cuestionario para el contenido del estudio.
- Si hay varias soluciones sintácticas posibles, selecciona la que esté respaldada por Base_Conceptual y por el caso más compatible con la estructura actual.
- Si no existe evidencia suficiente, no inventes: registra el caso en `Control_QA.md`.

# 5. CONTROL DE ENTRADAS

Antes de construir el MDD:

1. Verifica que los tres archivos puedan revisarse.
2. Recorre el 100 % del cuestionario.
3. Recorre `Base_Conceptual.txt` y `Ejemplos_MDD.txt` buscando criterios/casos aplicables.
4. Si falta el cuestionario, detén el proceso porque no existe fuente autoritativa del estudio.
5. Si falta la Base Conceptual o Ejemplos MDD, no inventes patrones. Genera únicamente aquello que pueda sostenerse con el cuestionario y registra la limitación en QA.

# 6. REVISIÓN DOCUMENTAL Y VISUAL DEL CUESTIONARIO

El cuestionario debe revisarse como contenido textual, estructural y visual.

Recorre de arriba hacia abajo y de izquierda a derecha:

- párrafos;
- tablas y celdas;
- encabezados y pies;
- numeraciones automáticas;
- columnas;
- cuadros de texto;
- formas;
- SmartArt;
- imágenes y capturas;
- objetos flotantes;
- contenido oculto;
- saltos de página;
- formato relevante;
- etiquetas HTML literales cuando existan;
- texto tachado, coloreado, sombreado o marcado como eliminado/deshabilitado.

Reglas de vigencia:

- Ignora contenido tachado cuando `IGNORAR_TEXTO_TACHADO = SI`.
- Ignora contenido en colores declarados no vigentes, por defecto rojo.
- Si solo una parte está tachada/no vigente, ignora solo esa parte.
- No elimines otros colores o formatos si no están configurados como no vigentes.
- No omitas contenido programable por estar insertado como imagen. Si una variable, cuota, escala, código o instrucción aparece visualmente y es legible, incorpórala en su posición documental.
- Si un elemento visual no puede leerse con certeza, no lo reconstruyas. Regístralo como `BLOQUEO_DE_COBERTURA` en QA.

La extracción textual no reemplaza la revisión visual.

No emitas este inventario como archivo independiente.

# 8. QUÉ DEBE CONVERTIRSE EN VARIABLE

Considera variable todo elemento que capture, almacene o represente un dato funcional del flujo.

Incluye, cuando estén documentados:

- preguntas categóricas;
- preguntas abiertas;
- números, edades, años, montos y mediciones;
- fechas;
- subcampos de matrices;
- campos de entrevistado;
- variables derivadas o de cuota explícitas;
- intros/textos informativos que formen parte funcional del flujo;
- variables técnicas requeridas por una regla explícita o plantilla autorizada.

Conviertas en variables independientes:

- títulos decorativos;
- nombres del estudio;
- versiones documentales;
- instrucciones sin captura;
- notas editoriales;
- enlaces sin captura;
- separadores de sección;
- categorías o filas de maquetación vacías.

Una introducción funcional debe modelarse como `info` y permanecer en su posición original; no acumules intros al final.

# 9. IDENTIFICADORES Y NOMENCLATURA

## 9.1 Identificador fuente

- Conserva el ID visible como evidencia funcional.
- No uses la etiqueta completa como ID.
- No reemplaces una etiqueta sin ID por una cadena enorme con guiones bajos.

## 9.2 Preguntas auxiliares sin ID

Si una pregunta auxiliar sin ID está asociada inequívocamente a una respuesta de una pregunta padre, genera:

`ID_PADRE_CODIGO`

Ejemplo conceptual: F3 + código 1 → `F3_1`.

Si no existe asociación padre-respuesta inequívoca, usa un identificador neutral y determinista, por ejemplo:

`SIN_CODIGO_001`, `SIN_CODIGO_002`, ...

Mantén siempre el wording en la etiqueta.

## 9.3 Normalización técnica para MDD

Normaliza en este orden:

1. Conserva letras, números y `_`.
2. Convierte puntos en `_`.
3. Convierte espacios y otros caracteres no admitidos en `_`.
4. Reduce `_` consecutivos a uno.
5. Elimina `_` sobrantes al inicio/final salvo que sean parte legítima del identificador técnico.
6. Si el ID comienza con número y el estándar del proyecto lo exige, aplica el prefijo neutral corroborado por la plantilla/caso; no inventes prefijos arbitrarios.
7. Conserva mayúsculas/minúsculas cuando sean significativas.
8. Si dos IDs colisionan, conserva el primero y agrega `_2`, `_3`, etc. según el orden documental, dejando constancia en QA.

Nomenclatura prohibida por error de normalización:

- `__Cod`
- `_C__Cod`

Para captura asociada usa un único separador, por ejemplo `_C_Cod` o la variante exacta corroborada por el proyecto.

# 10. ETIQUETAS, FORMATO Y HTML

La etiqueta debe conservar el contenido visible vigente del cuestionario sin introducir datos nuevos.

Reglas:

- Conserva wording, signos, acentos, mayúsculas/minúsculas y errores originales.
- Para iField, no antepongas automáticamente el número/ID de pregunta al fraseo cuando el identificador técnico ya lo representa y la plataforma lo muestra por separado.
- Para Dimensions Online, conserva o antepone el identificador solo si la plantilla autorizada lo exige.
- Conserva saltos de línea intencionales, separación entre fraseo e instrucciones y énfasis relevante.
- No elimines indicaciones parentéticas como `(MOSTRAR TARJETA)`, `(LEER OPCIONES)`, `(NO LEER)`, `(ENCUESTADOR: ...)`.
- Separa el wording de las instrucciones cuando técnicamente corresponda: wording en la etiqueta; instrucción de entrevistador en `_Osm_HiddenComment` o propiedad equivalente corroborada.
- Colocar la etiquetas HTML que correspondan en la estructura HTML. Lee el cuestionario y apóyate en base conceptual y en Base de ejemplos MDD

## 10.1 Regla nueva obligatoria de etiquetas HTML

- identifica etiquetas HTML presentes en el cuestionario o en la estructura técnica aplicable;
- conserva literalmente el HTML que forme parte del wording, instrucciones, saltos o formato funcional y sea compatible con el MDD/iField objetivo;
- no conviertas HTML válido a Markdown dentro de `MDD_PARCIAL.txt`;
- no elimines `<br>`, `<b>`, `<strong>`, `<i>`, `<font>` u otras etiquetas funcionales solo por ser HTML;
- si el cuestionario solo contiene formato Word y se requiere traducirlo a HTML para mantener negrita/saltos, utiliza únicamente el patrón compatible corroborado por Base_Conceptual/Ejemplos_MDD;
- preserva la anidación y cierre correcto de las etiquetas;
- escapa las comillas internas de forma compatible con cadenas MDD sin alterar el HTML.

La comparación de escalas puede ignorar diferencias puramente de marcado para detectar igualdad, pero la salida debe preservar el formato funcional correspondiente.

# 11. INSTRUCCIONES DEL ENTREVISTADOR Y `_Osm_*`

Las instrucciones dirigidas al entrevistador no deben desaparecer.

Cuando una instrucción esté asociada inequívocamente a una pregunta y Base_Conceptual/Ejemplos_MDD confirmen el patrón, usa `_Osm_HiddenComment` o la propiedad equivalente autorizada.

Ejemplos de instrucciones candidatas:

- MOSTRAR TARJETA;
- LEER / NO LEER;
- PROFUNDIZAR;
- ESPONTÁNEA;
- GRABAR / BACKCHECK como indicación operativa, sin convertirla por sí sola en lógica dentro del MDD.

## 11.1 Propiedades OSM

Detecta y conserva propiedades `_Osm_*` / `_OSM_*` cuando correspondan. Respeta exactamente el nombre y capitalización admitidos por el entorno; no renombres una propiedad válida solo para uniformizar el prefijo.

Propiedades conceptuales observadas que pueden ser aplicables, solo con evidencia:

- `_Osm_HiddenComment`
- `_Osm_IsRequired`
- `_Osm_IsNumbered`
- `_Osm_DisplayMode`
- `_Osm_ShowQuestionTexts`
- `_Osm_ShowChildNodeTexts`
- `_Osm_AllowWatermarks`
- `_Osm_CustomFunction`
- `_Osm_Placeholder`
- `_Osm_Label`
- `_Osm_QuestionLayoutID`
- `_Osm_ContentRuleID`
- `_Osm_HintFunction`

Reglas:

- No copies propiedades OSM solo porque una pregunta “se ve parecida” a un ejemplo.
- No deduzcas el significado universal de IDs numéricos de layout/content rule.
- Las propiedades OSM de presentación no sustituyen tipo, cardinalidad o estructura.
- `_Osm_HiddenComment` no debe usarse para guardar filtros, routing o terminaciones.
- `_Osm_CustomFunction` solo se asocia si existe una función requerida/corroborada para una validación que no puede resolverse declarativamente.

# 12. TIPOS Y CARDINALIDADES

Mapeo conceptual:

- RU / respuesta única → `categorical [1..1]` salvo opcionalidad explícita.
- RM sin máximo → `categorical [1..]` salvo mínimo distinto explícito.
- máximo N → `[1..N]` o `[0..N]` solo si la opcionalidad está documentada.
- exactamente N → `[N..N]`.
- mínimo N → `[N..]`.
- texto → `text` con longitud solo si existe evidencia/convención autorizada.
- entero → `long`.
- decimal → `double`.
- fecha/hora compatible → `date`.
- información → `info`.

Una lista de códigos numéricos sigue siendo categórica.

La cardinalidad pertenece al campo que captura la respuesta. En un loop/grid, la cantidad de filas no determina la cardinalidad del field interno.

No dupliques en JavaScript futuro una restricción que queda correctamente expresada en cardinalidad MDD, salvo una regla adicional del estudio.

# 13. RANGOS Y VALIDACIONES DECLARATIVAS

- Conserva rangos explícitos mínimos/máximos.
- No deduzcas rangos desde ejemplos o etiquetas.
- Las restricciones intrínsecas del propio campo deben declararse en MDD cuando el tipo lo soporte.
- Una validación que compara varias variables/iteraciones pertenece a la lógica y debe registrarse en `Resumen.md` como dependencia pendiente.
- No inventes regex para teléfono, correo, moneda, fechas o separadores.
- Solo genera `validation(...)` cuando exista una especificación literal/corroborada compatible.

# 14. CATEGORÍAS, CÓDIGOS Y `value`

Para cada alternativa capturable:

- conserva el código explícito;
- conserva el wording completo;
- conserva números entre paréntesis que formen parte del wording;
- no interpretes automáticamente esos números como códigos;
- no agregues categorías vacías producidas por filas/celdas de relleno;
- toda categoría capturable debe tener `value` según el patrón MDD autorizado;
- el identificador técnico de categoría debe usar un solo separador y evitar duplicaciones de `_`.

Sintaxis canónica conceptual:

`IDENTIFICADOR "ETIQUETA" [value = VALOR] other(...) ATRIBUTOS`

Orden obligatorio:

1. `value`
2. `other(...)` si aplica
3. `fix`, `exclusive`, `fix exclusive` u otros atributos compatibles.

Universaliza códigos 94/96/98/99 u otros. El comportamiento depende del wording, instrucciones y caso actual.

# 15. `other(...)`, EXCLUSIVIDAD Y FIJACIÓN

Genera `other(...)` únicamente si el cuestionario:

- dice explícitamente “especificar”; o
- muestra un campo abierto inequívocamente asociado; o
- documenta una captura adicional asociada.

La palabra “Otro/Otra/Otros” por sí sola no basta.

`fix`, `exclusive` y `fix exclusive` pueden aplicarse a categorías de cualquier pregunta categórica, incluido un field dentro de loop/grid, si existe evidencia.

Precedencia:

1. exclusividad explícita;
2. semántica especial inequívoca corroborada;
3. código técnico como evidencia secundaria, nunca universal;
4. fijación por regla de rotación.

# 16. ROTACIÓN Y ALEATORIZACIÓN

Distingue:

- aleatorización/rotación de categorías → atributo de la pregunta categórica (`ran`, `rot`, etc. según sintaxis corroborada);
- aleatorización de filas/iteraciones → `ran fields` u otra construcción autorizada;
- opciones excluidas de rotación → `fix` o `fix exclusive` cuando corresponda.

No confundas `ran` con `ran fields`.

# 17. LISTAS REUTILIZABLES `define/use`

Antes de emitir preguntas, compara escalas/conjuntos de categorías.

Crea una lista reutilizable cuando:

- el mismo conjunto base aparece más de una vez; o
- el cuestionario identifica una lista común; o
- Base_Conceptual y Ejemplos_MDD confirman que el patrón repetitivo debe centralizarse.

La igualdad debe considerar:

- cantidad de categorías;
- códigos;
- wording visible;
- cardinalidad relevante;
- captura asociada;
- atributos especiales.

Diferencias meramente de espacios o marcado no deben impedir detectar una lista común.

No metas dentro de una lista común categorías residuales/campos específicos que solo aplican a una pregunta si eso altera las demás reutilizaciones.

La lista `define` debe ubicarse antes de su primer uso.

# 18. LOOPS, GRIDS, BLOCKS Y SUBCAMPOS

## 18.1 Regla de interpretación

No conviertas automáticamente una tabla en grid.

Determina primero:

- qué entidad se repite;
- qué pregunta/captura es común;
- qué escala se comparte;
- si existe una segunda dimensión repetitiva;
- si las columnas son capturas diferentes o solo presentación.

## 18.2 Loop homogéneo

Usa loop cuando se repite la misma captura para múltiples entidades/atributos.

Patrón conceptual:

`PADRE "..." loop`
`{ filas con value } fields -`
`(`
`    Rp "..."`
`    TIPO/CARDINALIDAD`
`    { escala con value };`
`) grid/expand grid/variante corroborada;`

Reglas:

- las filas son iteraciones, no preguntas independientes;
- las filas tienen `value`;
- el field repetido contiene la cardinalidad;
- una escala común debe reutilizarse como un solo field;
- no fuerces `expand grid` de forma universal;
- selecciona `grid`, `expand grid`, `column grid`, `column expand grid`, `_Osm_DisplayMode = 3` u otra presentación solo con evidencia.

## 18.3 Block

Usa `block fields` para agrupaciones funcionales de controles heterogéneos, no para reemplazar una repetición que debería ser loop.

## 18.4 Nested loops

Usa loops anidados cuando existan dos dimensiones repetitivas reales, por ejemplo producto→atributo o empresa→driver.

No aplanes dimensiones jerárquicas en preguntas independientes sin evidencia.

# 19. MAXDIFF

Cuando el cuestionario documente MaxDiff:

- identifica el bloque completo como una sola estructura;
- conserva atributos, sets, columnas de elección y relaciones;
- busca un caso MaxDiff corroborado antes de decidir la sintaxis;
- reutiliza listas define/use cuando el conjunto de atributos lo permita;
- no inventes combinaciones/sets;
- si el estándar del proyecto utiliza una función custom de validación, declara `_Osm_CustomFunction` únicamente cuando la función y firma estén respaldadas por la Base/ejemplo;
- registra en `Resumen.md` cualquier validación cruzada que deba realizarse en lógica, por ejemplo impedir que “más” y “menos” sean la misma selección.

# 20. CUOTAS

Cuando el cuestionario declare una cuota:

- identifica la variable fuente y la variable de cuota como entidades diferenciables;
- conserva categorías, rangos y cruces documentados;
- genera la estructura/tablas de cuota únicamente si existe sintaxis corroborada para el entorno;
- si la asignación de cuota es dinámica y corresponde a JavaScript, declara las variables necesarias en MDD y registra la dependencia en `Resumen.md`;
- no inventes una tabla de cuota por analogía.

No omitas variables de cuota insertadas como imagen.

# 21. FECHAS Y HORAS

Usa `date` cuando el cuestionario capture fecha/hora y la plataforma objetivo lo soporte.

- rango propio de fecha → MDD;
- coherencia entre fecha y otra variable, como edad → lógica futura mediante función/evento si corresponde;
- no conviertas automáticamente una fecha en texto por ausencia de un ejemplo idéntico.

# 22. FOTOGRAFÍAS Y ATTACHMENTS

Para iField, cuando una pregunta sea de fotografía:

- conserva la interacción como variable compatible con las opciones documentadas, por ejemplo `Tomar foto` / `Foto adjuntada`;
- no inventes validación MDD o JavaScript para comprobar el archivo adjunto si Survey Builder/iField gestiona esa obligación;
- registra en QA/Resumen que la configuración física del attachment corresponde a la interfaz, salvo propiedades explícitas del proyecto.

# 23. INTROS E INFORMACIÓN

- Genera `info;` para intros/textos funcionales que deban mostrarse.
- Conserva la posición documental.
- No desplaces todos los `info` al final.
- No omitas `INTRO` solo por no capturar respuesta si es parte funcional del flujo.

# 24. VARIABLES TÉCNICAS Y DE SISTEMA

No agregues automáticamente variables de Dimensions/iField por existir en ejemplos.

Para iField:

- usa `Metadata(es-PE, Question, Label, SystemVariables = false)` cuando la versión del compilador lo soporte;
- excluye variables `System*`, `SHELL_*`, `Link ID` y equivalentes si no están requeridas;
- si un preprocesador de Dimensions participa, debe excluir campos de sistema no usados mediante una comprobación equivalente a `oField.IsSystem = False`.

Incluye una variable técnica solo si:

1. aparece en el cuestionario/estructura requerida;
2. es necesaria para una regla explícita;
3. pertenece a la whitelist/plantilla autorizada.

Variables como `ELIMI` es necesaria para terminación. No generalices el resto de variables Shell.

Siempre crear `ELIMI` y `GRACIAS_ELIMI`, colócalas en la zona definida por la plantilla y conserva sus definiciones autorizadas.

ELIMI "ESTA ENCUESTA SERÁ ELIMINADA POR NO CUMPLIR CON FILTRO DE LA ENCUESTA"
text [0..200];

GRACIAS_ELIMI "Gracias por participar"
info;


# 25. SEPARACIÓN MDD VS LÓGICA

Principio maestro:

- El MDD declara el contrato estable del dato.
- La lógica implementa lo que depende del estado de la entrevista.

No conviertas en MDD dinámico por imitación:

- show/hide dependiente de otra respuesta;
- filtros de categorías por contexto;
- filtros de iteraciones carry-forward;
- recodes derivados;
- routing/terminación;
- cálculos cruzados;
- validaciones entre variables;
- piping dinámico que requiere `setInsert`;
- inicio/detención de audio.

Estas reglas deben conservarse en `Resumen.md` como indicaciones/dependencias para el prompt de lógica.

# 26. CONSTRUCCIÓN DEL MDD

## 26.1 Encabezado

Para IFIELD, utiliza el encabezado compatible:

`Metadata(es-PE, Question, Label, SystemVariables = false)`

si el compilador objetivo admite esa forma.

Para Dimensions Online, utiliza el encabezado autorizado por la plantilla, sin `SystemVariables = false` cuando no corresponda.

## 26.2 Formato

- una declaración lógica por línea;
- sangría consistente;
- sin Markdown envolvente;
- sin comentarios editoriales;
- sin tabulaciones si el estándar usa espacios;
- no escapes `_`;
- llaves, paréntesis, comillas y puntos y coma balanceados;
- no dejes coma tras la última categoría;
- termina exactamente con `End Metadata`.
