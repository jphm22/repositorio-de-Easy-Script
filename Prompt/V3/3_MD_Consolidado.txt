# 3. QA DE ENTRADA — GATE E3

7. Renderiza e inspecciona visualmente el 100 % de las páginas del Word y contrasta imágenes, tablas, cuadros, formas, objetos flotantes, negritas y subrayados contra etapa 1 y MDD.

# 4. JERARQUÍA DE RESOLUCIÓN

1. Este prompt define el formato consolidado.
2. El cuestionario original define la intención funcional.
3. El Markdown de etapa 1 conserva la extracción normalizada y se usa para asegurar cobertura.
4. El MDD define la implementación técnica existente.
5. Las referencias externas nunca sustituyen al caso actual.

Cuando exista discrepancia:
- nombres técnicos, answer IDs, value, estructuras y tipos efectivos → conserva MDD;
- intención, condición y lógica funcional → conserva cuestionario;
- NO declares resuelta una discrepancia si ambas fuentes siguen siendo incompatibles;
- registra la incidencia en QA del consolidado.

# 5. INVENTARIOS INTERNOS

Construye internamente tres inventarios completos:
A. Word/Markdown funcional.
B. MDD técnico.
C. correspondencias.

Los inventarios deben incluir de forma diferenciada: INTRO, cuotas, listas reutilizables, grids padre, elementos de iteración, subcampos, escalas, categorías, instrucciones ENC y origen visual/textual. Ningún elemento se excluye por estar dentro de una imagen.

Cada variable/pregunta debe quedar como:
- CONFIRMADA;
- POSIBLE;
- NO_ENCONTRADA;
- TECNICA_SIN_PREGUNTA;
- ADMINISTRATIVA;
- SHELL.

No omitas silenciosamente elementos POSIBLE o NO_ENCONTRADA; deben aparecer en incidencias QA.

# 6. EMPAREJAMIENTO

Usa evidencia en este orden:
1. identificador equivalente;
2. identificador con diferencias sintácticas (`.`/`_`, espacios, case);
3. wording/etiqueta;
4. categorías y labels;
5. código visible ↔ `value`;
6. tipo/cardinalidad;
7. posición/contexto;
8. relación padre/subcampo;
9. dependencias e instrucciones vecinas.

Una coincidencia por posición sola nunca es suficiente.

# 7. TRAZABILIDAD DE IDENTIFICADORES Y CÓDIGOS

Para cada correspondencia confirmada conserva separadamente:
- `ID cuestionario`: identificador visible/Markdown.
- `ID MDD`: identificador técnico exacto.
- `Respuesta MDD`: answer identifier exacto, p. ej. `_1`, `_A1`.
- `Value MDD`: valor técnico, p. ej. `1`.
- `Código cuestionario`: código visible usado en PROG/reglas.

No trates `_1`, `1` y “código 1” como el mismo string. Pueden corresponder funcionalmente, pero son representaciones distintas y deben preservarse.

# 8. ORDEN DEL CONSOLIDADO

1. Shell/System existentes en MDD que sean relevantes downstream, en orden MDD.
2. Variables administrativas reservadas existentes antes del flujo si el MDD así lo define.
3. Variables del cuestionario con correspondencia confirmada, siguiendo el orden funcional del cuestionario, manteniendo subcampos dentro de su padre.
4. Variables administrativas finales (`ELIMI`, `ID_BASE`, `LINK` y otras reservadas) según su orden técnico.
5. Incidencias QA, si existen.

No inventes Shell ausentes.

# 11. CATEGORÍAS — FORMATO DOWNSTREAM SEGURO

##### Categorías:

| Respuesta MDD | Value MDD | Código cuestionario | Etiqueta | Exclusiva | Fija | Especificar | Tipo captura | Rango captura |
|---|---|---|---|---|---|---|---|---|

Reglas:
- `Respuesta MDD`: identificador técnico literal del MDD.

- `Especificar/Tipo captura/Rango captura`: derivados únicamente de `other(...)` o evidencia técnica equivalente en MDD, cruzada con cuestionario.

# 12. GRIDS, LOOPS Y BLOCKS

- Padre siempre antes de subcampos.
- Conserva el ID técnico exacto del padre y cada campo interno.
- Conserva el orden técnico de subcampos MDD.
- Padre usa `Tipo: GRID con varias variables` cuando represente estructura compuesta.
- Incluye `Sub-campos: N` cuando pueda contarse directamente.
- Si el loop usa filas/índices y `Rp`, representa claramente ambas capas; no colapses la estructura a una categórica simple.
- Los atributos numerados de una batería se consolidan como elementos de iteración, no como variables principales independientes.
- Para grid homogénea conserva un padre, la tabla de iteraciones y el subcampo común `Rp`/equivalente con su escala.
- Para grid heterogénea conserva un padre `block fields` y cada subcampo interno con su propio tipo/categorías.

Cuando existan iteraciones, agrega bajo el padre:

##### Elementos de iteración:

| Iteración MDD | Value MDD | Código cuestionario | Etiqueta |
|---|---|---|---|

Cada fila conserva el ID/value técnico literal del MDD y el código/etiqueta funcional del cuestionario. No confundas esta tabla con las categorías de respuesta del subcampo.

# 13. INDICACIONES FUNCIONALES

Las indicaciones proceden del cuestionario/etapa 1, no del MDD.

Conserva literalmente dentro de `Etiqueta` todo texto visible entre paréntesis, por ejemplo `(MOSTRAR TARJETA)`, y toda indicación al encuestador, incluida la marca `ENC`. Conserva también los marcadores `**...**` y `<u>...</u>`; no los conviertas en instrucciones funcionales ni los elimines.

Incluye:
- filtros;
- continuar/terminar;
- saltos;
- show/hide;
- piping;
- precarga;
- cálculo;
- selección requerida;
- exclusión entre preguntas;
- backcheck;
- inicio/detención de grabación;
- dependencias conjuntas.

No incluyas como indicación RU/RM, rango, rotación o atributos de categoría si ya tienen campo propio.

Conserva el `Código cuestionario` visible en las reglas. La etapa 4 lo resolverá contra `Respuesta MDD` y `Value MDD` usando la tabla consolidada.

# 16. DISCREPANCIAS E INCIDENCIAS QA

Si existe al menos una incidencia, agrega al final:

### Incidencias QA

| Severidad | ID cuestionario | ID MDD/candidato | Tipo de incidencia | Detalle | Acción downstream |
|---|---|---|---|---|---|

Severidad:
- CRITICA: puede producir error de ejecución, terminación incorrecta o pérdida de datos.
- ALTA: altera elegibilidad/flujo.
- MEDIA: altera presentación, rotación o captura.
- BAJA: diferencia documental sin impacto funcional inmediato.

Ejemplos:
- variable no encontrada;
- variable visible en imagen/tabla/forma no convertida;
- INTRO omitido;
- cuota omitida o mapping de cuota incompleto;
- texto entre paréntesis, ENC, negrita o subrayado perdido;
- categoría con etiqueta vacía;
- opción Otro con captura no solicitada;
- escala repetida sin lista reutilizable;
- coincidencia solo posible;
- código cuestionario sin answer/value MDD;
- rango distinto;
- exclusividad/fijación distinta;
- Shell requerida ausente;
- estructura grid/loop no equivalente;
- backcheck sin límites;
- regla ambigua.

`Estado QA = APROBADO` solo si no existen incidencias CRITICA/ALTA y no hay correspondencias POSIBLE/NO_ENCONTRADA necesarias para lógica.

# 17. QA DE SALIDA — GATE E3→E4

## 17.1 Cobertura funcional
- Cada variable de etapa 1 está confirmada o registrada en incidencias.
- Cada regla PROG funcional está asignada una sola vez.
- Todos los backchecks están representados.
- Cada página/objeto visual fue revisado y todo contenido funcional está confirmado o registrado como incidencia.
- Todos los INTRO, cuotas e indicaciones ENC/parentéticas están representados.

## 17.2 Cobertura técnica
- Cada ID MDD, answer ID y value usado existe literalmente en el MDD.
- Shell y administrativas se preservan solo si existen.
- Padres/subcampos/loops no se colapsaron.
- Atributos numerados, iteraciones, campos y escalas de grid permanecen diferenciados.
- Toda lista MDD y cada uno de sus usos están trazados.

## 17.3 Correspondencia
- `Código cuestionario` no se confundió con `Respuesta MDD`.
- Cada categoría mapeada conserva etiqueta y value.
- Las categorías mantienen el orden técnico por código y no hay etiquetas vacías espurias.
- Otro/other solo aparece con solicitud explícita de especificación.
- Ninguna coincidencia POSIBLE se presenta como CONFIRMADA.

## 17.4 Formato
- Markdown estándar; `<u>...</u>` se permite exclusivamente dentro de etiquetas para conservar subrayado.
- No hay tablas vacías.
- Campos permitidos y orden consistente.
- `Estado QA` coincide con incidencias.
- Negrita y subrayado conservan exactamente su alcance.

Si se detecta error corregible, corrige y repite QA.
