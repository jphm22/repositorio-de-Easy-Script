# 5. INVENTARIO DE REGLAS FUNCIONALES

Recorre el 100 % de `cuestionario.md` y `estructura_consolidada.md` e inventaría cada instrucción programable:
- filtros/terminaciones;
- navegación/saltos;
- show/hide;
- piping;
- precargas;
- Shell prefill/recode;
- validación de rango;
- validaciones entre campos;
- loops/grids;
- cálculo/autocode;
- cuotas;
- randomización cuando requiera JS;
- backcheck y grabación;
- consentimiento de grabación;
- control de respuestas;
- reglas conjuntas.
- cada condición subordinada, excepción, alternativa `Y/O`, prioridad y acción incluida en una instrucción compuesta.

Cada regla recibe un `RULE_ID` determinista: `R001`, `R002`, ... según orden funcional del cuestionario.

Descompón una instrucción compuesta en reglas atómicas cuando contenga acciones o resultados distintos, pero conserva explícitamente sus relaciones `AND`, `OR`, `NOT`, precedencia y dependencia. Construye internamente una tabla de verdad/casos de decisión para toda condición combinada antes de generar código. Ninguna frase funcional puede quedar absorbida en un resumen que omita condiciones.

## 5.1 Propiedad y lógica independiente por variable

Asigna cada `RULE_ID` a una `VARIABLE_PRIMARIA` inequívoca: la variable cuyo evento dispara o contiene la lógica. Otras variables se registran como dependencias, sin perder la propiedad primaria.

El JavaScript se organiza en bloques independientes por `ID MDD`:
- comentario de apertura `// VARIABLE: <ID_MDD>`;
- uno o más comentarios `// RULE_ID: RNNN`;
- condición y acción completas de esa variable;
- comentario de cierre si el estilo EasyScript lo requiere.

No ocultes lógica específica dentro de una función auxiliar genérica. Cada regla debe poder localizarse desde variable → `RULE_ID` → bloque JS → condición fuente.

## 5.2 Política restrictiva de funciones auxiliares

Por defecto, implementa la lógica directamente dentro del bloque/evento de cada variable.

Solo puedes crear o invocar una función auxiliar si la base de conocimiento contiene una referencia válida que demuestre para esa misma finalidad:
1. nombre o patrón de la función;
2. definición completa;
3. firma/parámetros;
4. evento y alcance compatibles;
5. caso/archivo/estudio de procedencia identificable.

Para cada helper autorizado asigna `HELPER_REF` y registra `HELPER_REF | función | referencia EasyScript | definición encontrada | adaptación | RULE_ID usuarios`. Copia/adapta la definición completa antes del primer uso. Si falta cualquiera de esos elementos, NO uses el helper: desarrolla la lógica directamente en cada variable. Está prohibido inventar wrappers, utilidades, alias o abstracciones por conveniencia.

# 7. RECUPERACIÓN OBLIGATORIA EN EASYScript

Antes de implementar cada regla:
1. Busca casos con la misma finalidad técnica, no solo el mismo nombre.
2. Si hay al menos dos casos relevantes, compara dos.
3. Evalúa semejanza por tipo de variable, RU/RM, loop/block, evento, Shell, navegación, grabación, métodos y dependencias.
4. Extrae el patrón técnico común.
5. Adáptalo exclusivamente a símbolos reales del estudio.
6. No copies nombres ni reglas de otros estudios.
7. Si no existe caso, registra `SIN CASO DE REFERENCIA EN BASE DE CONOCIMIENTO`.
8. Si el patrón utiliza una función auxiliar, recupera también su definición completa y crea `HELPER_REF`; una mera llamada sin definición no constituye evidencia.

No uses un método/evento no demostrado en la base o no autorizado explícitamente por el entorno. Si falta evidencia suficiente, bloquea la regla en lugar de inventar API.

# 8. MODELO DE TRAZABILIDAD POR REGLA

Para cada `RULE_ID` conserva:
- texto/regla funcional fuente;
- ID cuestionario;
- ID MDD;
- variable primaria;
- answer ID/value afectados;
- familia;
- dependencias;
- evento seleccionado;
- casos EasyScript consultados;
- patrón elegido;
- adaptación;
- expresión lógica completa normalizada, incluidos `AND`/`OR`/`NOT` y precedencia;
- `HELPER_REF` o `SIN_HELPER`;
- estado: IMPLEMENTADA | PARCIAL | BLOQUEADA | NO_APLICA;
- confianza: ALTA | MEDIA | BAJA;
- referencia al bloque de variable y marcador `RULE_ID` del JS generado.

# 9. VALIDACIÓN CRUZADA ANTES DE GENERAR CÓDIGO

Para cada regla:
1. variable existe en MDD;
2. answer ID/value existe;
3. estructura simple/RM/loop/grid/block es conocida;
4. método es compatible con esa estructura;
5. todas las dependencias estarán disponibles en el evento elegido;
6. reglas conjuntas no se evalúan prematuramente;
7. destino de navegación existe;
8. terminaciones usan la variable administrativa correcta y existente;
9. no queda una grabación activa en una salida anticipada;
10. el patrón EasyScript es compatible.
11. la condición generada es lógicamente equivalente a todas las condiciones, excepciones y prioridades de la fuente;
12. la variable primaria contiene su propia implementación o un helper con `HELPER_REF` válido y definición trazada;
13. una cuota utiliza únicamente mappings y variables fuente confirmados.

# 10. DISCREPANCIAS Y BLOQUEOS

Registra discrepancias:
- código visible sin answer ID/value;
- variable del cuestionario ausente en MDD;
- rango diferente;
- exclusiva/fija distinta;
- rotación distinta;
- dependencia imposible;
- API/evento sin referencia;
- Shell ausente;
- regla ambigua;
- ejemplo EasyScript incompatible o incompleto.
- función auxiliar sin referencia/definición válida;
- condición fuente omitida o simplificada;
- cuota o variable visual ausente;
- grid aplanado o método aplicado al nivel equivocado.

Severidad:
- CRITICA
- ALTA
- MEDIA
- BAJA

Una regla BLOQUEADA:
- no genera código activo que dependa del elemento faltante;
- genera únicamente comentario `TODO [RULE_ID]: ...` explicando exactamente qué falta;
- el JS debe seguir siendo sintácticamente válido.

# 11. BACKCHECK Y GRABACIÓN

Realiza auditoría global de audio independiente del resto.

No basta con que la infraestructura de grabación exista.

## 11.1 Shell
Si existen, inspecciona:
- `SHELL_RECORDING_CONFIRMATION`
- `SHELL_CHAINID`

Determina desde MDD, no por suposición:
- answer ID real de aceptación;
- answer ID real de rechazo;
- tipo de `SHELL_CHAINID` y método compatible.

No asumas `_A1` salvo que el MDD lo confirme.

## 11.2 Seguridad del segmento
Para cada inicio:
- consentimiento validado antes de iniciar;
- nombre de audio usa un identificador de entrevista real;
- existe detención explícita;
- filtros/saltos/terminaciones contemplan stop cuando corresponda;
- no hay inicios duplicados por reentrada sin control.

Si no puede determinarse el punto exacto de inicio/fin, BLOQUEA ese segmento. No elijas una pregunta arbitraria.

# 12. SHELL PREFILL Y RECODE

Solo genera mapeos Shell→local si:
- la Shell existe;
- la variable local existe;
- el mapping de categorías/value está documentado o inequívocamente respaldado por el caso actual;
- el evento/método está respaldado por EasyScript.

No supongas equivalencias por etiquetas parecidas.

# 13. FILTROS Y TERMINACIONES

- Evalúa la condición cuando todas sus dependencias estén disponibles.
- Para condiciones conjuntas, usa el último punto lógico necesario, salvo terminación anticipada inequívoca.
- Antes de navegar a `ELIMI`, verifica que `ELIMI` exista literalmente.
- Si hay grabación activa, detén primero cuando corresponda.
- No uses `Código cuestionario` como answer ID; resuelve mediante el consolidado.

# 14. LOOPS, GRIDS Y BLOCKS

No apliques métodos de variable simple a estructuras compuestas.

Antes de usar iteradores:
- verifica tipo exacto en MDD;
- identifica campo interno real;
- distingue padre, elemento de iteración, subcampo capturable y categoría de escala;
- verifica que los atributos numerados no hayan sido transformados en preguntas independientes;
- usa solo `getIteration`, `getIterator` o método equivalente si está demostrado por EasyScript para esa estructura.

Si no existe patrón compatible, BLOQUEA en vez de inventar una ruta.

## 14.1 CUOTAS

Para cada variable con `Función técnica: Cuota`:
1. crea al menos un `RULE_ID` de familia `QUOTA_ASSIGNMENT` si existe asignación/derivación funcional;
2. identifica la variable de cuota como `VARIABLE_PRIMARIA` y enumera todas las variables fuente;
3. construye una matriz exhaustiva `condición fuente → categoría/Respuesta MDD/Value MDD de cuota`;
4. respeta intervalos, inclusividad de límites, prioridades, casos sin asignación y solapamientos;
5. implementa la asignación directamente en el bloque de la cuota, salvo helper con `HELPER_REF` válido;
6. bloquea la regla ante mapping incompleto, solapado o símbolo ausente; nunca asigna por semejanza de etiqueta.

Verifica de forma explícita cuotas visibles solo en imágenes/tablas y cuotas secundarias como variables separadas. No combines cuotas distintas.

# 15. CONVENCIONES DEL JAVASCRIPT FINAL

El archivo `[BASE_ESTUDIO].logic.js` debe:
- ser JavaScript sintácticamente válido;
- no contener Markdown;
- usar nombres exactos del MDD;
- agrupar código primero por variable y dentro de ella por `RULE_ID`;
- declarar antes de su uso únicamente helpers autorizados por la sección 5.2 y acompañarlos de comentario `// HELPER_REF: <ID>`;
- evitar variables globales innecesarias;
- no duplicar listeners para la misma regla/evento;
- contener `TODO [RULE_ID]` solo como comentarios cuando una regla esté bloqueada;
- no contener pseudocódigo activo;
- mantener el estilo técnico confirmado por EasyScript.

Orden obligatorio:
1. definiciones de helpers autorizados, solo si existen y con `HELPER_REF`;
2. bloques `// VARIABLE: <ID_MDD>` en el orden funcional del cuestionario;
3. dentro de cada bloque, `RULE_ID` en orden ascendente;
4. TODO bloqueados dentro del bloque de su variable; solo los TODO sin variable confirmada se agrupan al final.
