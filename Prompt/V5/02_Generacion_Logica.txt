# 9. RECUPERACIÓN DE PATRONES EN BASE DE CONOCIMIENTO

Antes de implementar cada familia:

1. Busca casos funcionalmente similares en toda `Base_Conocimiento.txt`.
2. Compara estructura MDD, tipo de variable, evento, nivel de filtro y dependencia.
3. Si existen varios casos, compara al menos dos cuando sea útil y estén disponibles.
4. Extrae el patrón común.
5. Adapta únicamente nombres/códigos/estructuras del estudio actual.
6. Si no hay caso comparable, registra `SIN CASO DE REFERENCIA EN BASE DE CONOCIMIENTO`.
7. No inventes firmas de API por analogía.

# 10. NIVEL CORRECTO DE INTERVENCIÓN

Aplica la regla en el nivel mínimo correcto:

- pregunta completa → `show()/hide()` o mecanismo equivalente;
- categorías → `showAnswers()/hideAnswers()` o equivalente;
- filas/entidades de loop → `filterIterations()/showIterations()/hideAllIterations()` o equivalente;
- texto dinámico → insert/piping;
- derivación → variable independiente + asignación;
- salida → routing/terminación;
- validación transversal → función/evento.

No uses filtros de categorías para resolver un carry-forward de filas.
No uses filtrado de iteraciones si solo debe cambiar una respuesta.

# 11. SELECCIÓN DEL EVENTO

Elige el evento por el momento funcional, no por costumbre.

- `onBeforeNavigateTo`: preparar estado antes de presentar; show/hide; filtros de categorías; filtros de iteraciones; inserts; piping; limpieza/reset necesaria para reentrada.
- `onEntrance`: inicialización operativa al entrar; inicio de backcheck/grabación cuando esté corroborado.
- `onInputChange`: cálculos/feedback que deben actualizarse durante la respuesta.
- `onNext`: recodes posteriores a captura; routing/terminación; validaciones de salida; parada de grabación; asignaciones que dependen de la respuesta recién capturada.
- función custom: validación específica asociada por el mecanismo OSM correspondiente.

No uses `onBeforeNavigateTo` indiscriminadamente para toda asignación. Úsalo cuando el estado deba estar listo antes de mostrar el nodo.

# 12. REGLAS DE JAVASCRIPT

- Respeta exactamente namespaces y rutas existentes.
- Usa `OSM.Survey` y objetos intermedios solo si están documentados por la Base/ejemplo compatible.
- Respeta mayúsculas/minúsculas de variables/categorías.
- No inventes `getIteration`, `getIterator`, `getAnswers`, `setAnswers`, `setInsert`, etc. si la firma no está respaldada.
- Evita aliases no definidos.
- Declara variables auxiliares con alcance claro.
- Mantén llaves, paréntesis, comillas y callbacks balanceados.
- No generes código recortado ni `...` dentro del JavaScript final.
- Un `TODO` debe contener la razón técnica concreta y el elemento faltante.

# 13. PROHIBICIÓN DE `return` DESNUDO EN LISTENERS

No uses `return` desnudo como mecanismo de validación/control de flujo dentro de `addEventListener`.

Reserva retornos estructurados, por ejemplo `{status: ..., message: ...}`, para funciones de validación invocadas por el mecanismo OSM que los espera.

Dentro de listeners, controla el flujo mediante condiciones/eventos compatibles, no mediante un `return` que pueda romper la ejecución esperada.

# 14. EVITAR CÓDIGO REDUNDANTE

No generes cadenas innecesarias de `If/Show/Goto`.

- Si una pregunta se muestra naturalmente, no agregues `show()`.
- Si la navegación normal resuelve la continuidad, no agregues `Goto`.
- Si una cardinalidad ya limita respuestas, no reprogrames el mismo máximo.
- No copies un patrón largo de otro estudio cuando una condición mínima compatible resuelve la regla.

# 15. RESTABLECIMIENTO DEL ESTADO

Para filtros dependientes del contexto que puedan reevaluarse por retroceso/edición:

1. restablece el dominio/estado correspondiente;
2. aplica el filtro actual;
3. limpia respuestas/comments de elementos que dejan de ser válidos si el caso/estándar lo requiere;
4. presenta el nodo.

Evita residuos de una visita anterior.

# 16. FILTROS Y TERMINACIONES

Para cada filtro:

- verifica códigos existentes;
- verifica inclusión/exclusión exacta;
- espera a que todas las dependencias estén disponibles;
- no evalúes una condición conjunta prematuramente;
- conserva recodes/flags/motivo necesarios antes de terminar;
- detén grabación antes de una salida anticipada cuando corresponda;
- distingue terminación por filtro (`ELIMI` o equivalente) de cierre final (`SHELL_CLOSE` o equivalente).

No uses una pantalla de cierre como prueba de que una pregunta es la última. El orden funcional viene del cuestionario.

# 17. RANGOS, LÍMITES Y OPERADORES

Para toda regla numérica/categórica:

- límite inferior;
- límite superior;
- inclusión/exclusión;
- `>`, `>=`, `<`, `<=`, `===`, `!==`;
- tipo real comparado;
- huecos o solapes;
- código destino.

Deben coincidir exactamente con el cuestionario y MDD.

No compares strings con números mediante igualdad estricta sin conversión compatible.
Usa `parseInt`, `parseFloat`, comprobación de `NaN`, `null` y `undefined` cuando corresponda al patrón y tipo real.

# 18. CARRY-FORWARD, LOOPS Y GRIDS

Cuando una selección previa determine qué filas se evalúan después:

- conserva el universo estructural del loop en MDD;
- filtra iteraciones en la pregunta destino;
- no ocultes categorías internas para simular el filtrado de filas;
- usa el nivel de loop correcto en nested loops;
- verifica `getIteration()`/iterador y rutas internas.

Para matrices sucesivas:

- puede ser necesario ocultar la pregunta completa si no hay ninguna fila elegible;
- y además filtrar iteraciones cuando sí existe al menos una fila.

# 19. MAXDIFF

Cuando el estudio use MaxDiff:

- verifica estructura MDD completa;
- utiliza únicamente el patrón de validación corroborado;
- comprueba que las selecciones de dimensiones incompatibles no puedan coincidir cuando esa sea la regla;
- no inventes sets ni métodos;
- si falta el field/estructura requerida, marca la regla como BLOQUEADA.

# 20. RECODES Y VARIABLES DERIVADAS

- No sobrescribas la variable fuente si el recode representa un dato diferente.
- Asigna a una variable derivada existente en MDD.
- Ejecuta el recode después de que la fuente esté disponible.
- Si la derivada debe ser de solo lectura y el patrón lo exige, aplica el mecanismo documentado.
- Verifica que toda ruta válida asigne/limpie el valor correcto para evitar residuos.

# 21. CUOTAS

Para cada cuota:

- identifica fuente y destino;
- ejecuta la asignación cuando la fuente ya esté capturada;
- verifica rangos/códigos;
- audita funciones auxiliares;
- no uses categorías ocultas/no válidas como respuestas reales;
- conserva trazabilidad de variable fuente → variable de cuota;
- no inventes sintaxis de quota si la configuración se realiza fuera del código.

# 22. PIPE-INS, PLACEHOLDERS E INSERTS

Audita y genera de punta a punta:

1. fuente declarada;
2. placeholder/insert destino;
3. momento en que se llena;
4. todas las ramas que lo alimentan;
5. limpieza cuando cambia la fuente;
6. texto correcto por producto/posición;
7. ausencia de valores heredados/vacíos en rutas válidas.

Detecta errores de copy-paste entre primer/segundo/tercer producto o preguntas espejo.
