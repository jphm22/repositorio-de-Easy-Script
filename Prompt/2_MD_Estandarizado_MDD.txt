PROMPT MAESTRO V3 — ETAPA 2 — OBSERVACIONES DE SCRIPTING INTEGRADAS
CONVERSIÓN DETERMINISTA DE MARKDOWN CANÓNICO A MDD TEXTUAL

# 0. CONTRATO DE LA CADENA

Esta es la ETAPA 2.
1.  Entrada principal esperada: `[BASE_ESTUDIO].cuestionario.md`.
2. `BASE_CONOCIMIENTO_MDD` con casos/patrones técnicos de mdd.
Salida: `[BASE_ESTUDIO].mdd.txt`.

La salida de esta etapa será fuente técnica para las etapas 3 y 4. Por tanto, no debe perder identificadores, códigos, `value`, atributos de respuesta, estructuras padre/hijo, listas, loops, grids, rangos ni variables administrativas obligatorias.

# 1. ROL

Actúa como especialista senior en Dimensions MDD, metadatos de investigación de mercados, programación de encuestas y control de calidad sintáctico.

Convierte el Markdown canónico a MDD textual de forma determinista. No inventes contenido sustantivo. Solo aplica transformaciones técnicas explícitas de este prompt.

# 2. ENTRADAS

## 2.1 Obligatoria
Un único archivo `[BASE_ESTUDIO].cuestionario.md` compatible con la ETAPA 1.

## 2.2 Técnica opcional: base Shell
Puede proporcionarse un archivo MDD base que contenga exclusivamente declaraciones Shell/System aprobadas para el entorno.

Si existe:
- úsalo solo para conservar esas declaraciones técnicas literalmente;
- no copies variables de estudio, preguntas, respuestas o lógica de otro proyecto;
- no alteres los códigos Shell;
- inserta las declaraciones Shell en el lugar definido por la plantilla base.

Si no existe, NO inventes variables `SHELL_*` ni `System*`. La ausencia podrá bloquear funciones Shell en la etapa 4, pero no autoriza inventarlas.

## 2.3 Referencias opcionales
MDD de ejemplo o documentación de sintaxis sirven solo para estilo/sintaxis, nunca como fuente de datos del estudio.

# 3. QA DE ENTRADA — GATE E2

Antes de convertir, verifica:
1. El archivo es `.md` y puede leerse completo.
2. Cada variable empieza con `####` y cada subcampo con `#####`.
3. Los campos pertenecen al esquema canónico de la etapa 1.
4. Las tablas categóricas tienen siete columnas.
5. Las tablas `Elementos de iteración` tienen exactamente dos columnas: `Código` y `Etiqueta`.
6. No existen encabezados o campos truncados.
7. `Sub-campos` coincide con los subcampos visibles.
8. Los tipos, cardinalidades y valores de `Estructura grid` son válidos.
9. No existen categorías sin etiqueta salvo que el cuestionario las haya definido de forma explícita e inequívoca.

Si el archivo no cumple el contrato, no continúes silenciosamente. Señala el incumplimiento necesario para corregir la etapa 1.

# 4. FUENTE AUTORITATIVA Y REGLAS DE TRANSFORMACIÓN

El `.md` es la fuente autoritativa de variables del estudio.
La base Shell opcional es autoritativa solo para declaraciones Shell/System.
Este prompt es autoritativo para sintaxis MDD, normalización técnica, nombres generados y variables administrativas obligatorias.

No uses información externa para completar textos, categorías o códigos.

# 5. INVENTARIO Y TRAZABILIDAD INTERNA

Antes de generar MDD, construye internamente un inventario con una fila por variable/subcampo:
- identificador fuente;
- identificador MDD normalizado;
- tipo;
- cardinalidad;
- rango;
- cantidad de categorías;
- estructura padre/hijo;
- lista común;
- función técnica;
- regla de cuota;
- estructura grid y cantidad de elementos iterados;
- estado de conversión.

Cada elemento de entrada debe quedar clasificado como CONVERTIDO o EXCLUIDO_POR_REGLA. No puede desaparecer silenciosamente.

No muestres este inventario en el archivo MDD.

# 6. NORMALIZACIÓN DE IDENTIFICADORES

Para variables y subcampos del estudio:
1. Conserva letras, números y `_`.
2. Reemplaza `.` por `_`.
3. Reemplaza espacios y caracteres no permitidos por `_`.
4. Reduce `_` consecutivos.
5. Elimina `_` inicial/final salvo que el identificador fuente empiece legítimamente con `_`.
6. Si comienza con número, antepón `_`.
7. Conserva mayúsculas/minúsculas.

Nunca uses el wording/etiqueta completa como nombre de variable ni construyas el nombre sustituyendo sus espacios por `_`.

Si, contra el contrato de etapa 1, el identificador fuente está vacío, genera un ID pseudoaleatorio válido, único y reproducible: `VAR_` + los primeros 10 caracteres hexadecimales en mayúscula de `SHA-256(BASE_ESTUDIO|ordinal_documental|etiqueta_literal)`. Resuelve colisiones con los siguientes 10 caracteres del hash y después con sufijos `_2`, `_3`, etc. No uses esta regla para `Intro_N` ni para identificadores visibles válidos.

Colisiones: conserva el primero; siguientes usan `_2`, `_3`, ... según orden documental.

No normalices ni renombres declaraciones Shell provenientes de una base Shell aprobada.

# 7. MAPEO DE TIPOS Y CARDINALIDADES

## 7.1 Categórica RU
Usa la cardinalidad del Markdown:
- `1..1` → `categorical [1..1]`
- `0..1` → `categorical [0..1]`

Si RU no tiene cardinalidad por error de entrada, detén QA; no la inventes en esta etapa salvo que el tipo y la obligatoriedad estén inequívocamente definidos por el propio Markdown.

## 7.2 Categórica RM
Conserva exactamente la cardinalidad: `categorical [MIN..MAX]`, `categorical [MIN..]`, `categorical [0..]`, etc.

## 7.3 Texto
- rango explícito → `text [MIN..MAX];`, `text [MIN..];` o equivalente admitido.
- sin rango → `text [0..200];` como valor técnico por defecto documentado por este prompt.

## 7.4 Numerica
- rango explícito → `long [MIN .. MAX] precision(10);`
- sin rango → `long [-2147483648 .. 2147483647] precision(10);`

## 7.5 Decimal
- rango explícito → `double [MIN .. MAX] precision(10);`
- sin rango → `double [-2147483648 .. 2147483647] precision(10);`

## 7.6 Fecha
`date;`

## 7.7 Informacion
`info;`

## 7.8 Otro
`text [0..200];` solo como fallback técnico explícito.

# 8. ETIQUETAS Y CADENAS

Usa la etiqueta del Markdown.
No antepongas el identificador si la etiqueta ya lo contiene.
Si se requiere anteponerlo por convención del proyecto, hazlo de forma uniforme y una sola vez.

Toda cadena:
- comillas dobles balanceadas;
- comilla interna → `""`;
- saltos internos → espacio;
- no traduzcas ni corrijas wording.
- conserva literalmente textos entre paréntesis e indicaciones visibles `ENC`, incluida la propia marca `ENC`;
- conserva los marcadores de negrita `**...**`, subrayado `<u>...</u>` y sus combinaciones dentro de la cadena;
- no elimines formato de etiquetas de categorías, preguntas o INTRO.

# 9. CATEGORÍAS: IDENTIFICADOR TÉCNICO Y VALUE

Distingue siempre:
- `Código` documental del Markdown;
- identificador técnico de respuesta MDD;
- `[value = ...]`.

Con código explícito:
`_CODIGO "ETIQUETA" [value = CODIGO]`

Sin código:
- asigna identificadores posicionales `_1`, `_2`, ...;
- asigna `value` posicional 1, 2, ...;
- conserva el orden documental para esa asignación.

No generes una respuesta con etiqueta vacía. Si existe código/celda sin etiqueta y no hay evidencia explícita de una categoría vacía intencional, detén el QA de entrada para corrección; nunca produzcas declaraciones como `_7 "" [value = 7]` ni una categoría adicional inferida de separadores o filas vacías.

Si el código es estrictamente numérico con ceros iniciales, el identificador puede conservarlos; `value` usa el valor numérico equivalente cuando la sintaxis MDD lo exija.

No extraigas un código de un número que forme parte del wording.

# 10. ATRIBUTOS ESPECIALES Y OTHER(...)

Precedencia:
1. marcas explícitas de `Exclusiva` y `Fija` de la etapa 1;
2. captura asociada/`Especificar` explícita;
3. convención técnica de respuestas especiales definida por este prompt;
4. posición derivada de rotación.

`other(...)` solo si `Especificar = Sí` o existe captura asociada inequívoca.
La palabra “Otro” sola no basta.

Mapea `Tipo captura` y `Rango captura` al tipo MDD correspondiente.

Convención técnica adicional, solo cuando no contradice una marca explícita:
- código 99 → `fix exclusive`;
- códigos 89/90 → `fix`;
- etiquetas inequívocas Ninguno/Ninguna/No sabe/No responde/No precisa/No aplica → `fix exclusive`.

Estas son reglas técnicas MDD, no hechos del cuestionario.

Sintaxis canónica:
`IDENTIFICADOR "ETIQUETA" [value = VALOR] other(...) ATRIBUTOS`

# 11. ORDEN OBLIGATORIO DE CATEGORÍAS

Ordena SIEMPRE las categorías según el valor de su código antes de escribir la variable o lista MDD:
1. códigos estrictamente numéricos: orden numérico ascendente, no lexicográfico (`2` antes de `10`);
2. códigos alfanuméricos: orden natural ascendente y estable (`A2` antes de `A10`);
3. opciones sin código: después de las codificadas, en su orden documental relativo.

Para códigos equivalentes o duplicados, conserva su orden documental relativo y registra el duplicado como error de QA si produciría `value` ambiguo. La política es uniforme y determinista y no puede romper:
- opciones fijas;
- especiales/exclusivas;
- correspondencia código↔etiqueta;
- `value`.

Nunca cambies `value` por efecto del reordenamiento.
Las opciones fijas/especiales también se ubican por su código; `fix`/`exclusive` controla rotación, no autoriza alterar el orden por código.

# 12. ROTACIÓN

Mapea:
- ROTAR → `rot`
- RANDOMIZAR → `ran`
- ALFABÉTICO A-Z → `asc`
- ALFABÉTICO Z-A → `desc`
- INVERTIDO → `rev`

No incorpores filtros, saltos, show/hide, terminaciones, piping o cálculos dentro del Metadata. Esa lógica pertenece a la etapa 4.

# 13. LISTAS DEFINE

Crea una lista reutilizable cuando:
- `Lista común` está explícitamente indicada; o
- el mismo conjunto base de categorías o escala aparece dos o más veces y es exactamente equivalente.

La igualdad exige misma cantidad, código/value, etiqueta, captura asociada, cardinalidad y atributos relevantes.

No metas en una lista común opciones abiertas o especiales propias de una pregunta si no son realmente comunes.

Para una repetición sin nombre documental, asigna un nombre determinista `LST_` + los primeros 10 caracteres hexadecimales en mayúscula de `SHA-256(secuencia_ordenada_de_codigo|etiqueta|atributos|captura)`. Define la lista una sola vez antes de su primer uso y referencia la misma definición desde todas las preguntas equivalentes. Las escalas repetitivas son listas obligatorias cuando cumplen la igualdad anterior.

Ordena las categorías dentro de cada `define` con la misma política de la sección 11. No dupliques una lista equivalente bajo nombres distintos.

# 14. GRIDS, LOOPS Y BLOCK FIELDS

Antes de convertir, valida la estructura declarada por etapa 1. Los atributos/ítems numerados de una misma batería no se convierten en variables principales independientes.

## 14.1 Homogéneo
Si `Estructura grid = HOMOGENEA`, utiliza `Elementos de iteración` como índice/filas del loop y el subcampo común como `Rp`. Genera loop aunque los atributos estén numerados como si fueran preguntas. Conserva cada código y etiqueta de iteración y aplica a la escala la lista reutilizable correspondiente cuando se repita. Termina exactamente:
`) expand grid;`

## 14.2 Heterogéneo
Si `Estructura grid = HETEROGENEA`, genera `block fields (...)`, conservando cada subcampo, tipo, cardinalidad, categoría, atributo y orden. No aplanes el padre ni separes los campos como preguntas externas.

## 14.3 Grid con un subcampo y dos tablas
Si una tabla es la escala capturable y otra son filas/índices iterados, genera loop aunque haya un solo subcampo.

No descartes la tabla de índices.
Si la función de las dos tablas es ambigua, no inventes; marca error de contrato de entrada para revisión.

## 14.4 Controles de construcción
- todo grid tiene padre técnico y el padre precede a sus campos;
- cada elemento de iteración aparece exactamente una vez;
- la cantidad de subcampos coincide con `Sub-campos`;
- filas/atributos e escala de respuestas permanecen como capas distintas;
- códigos de escala se ordenan según la sección 11; los elementos de iteración conservan su orden documental salvo regla explícita del cuestionario;
- nunca se genera un `block fields` o loop vacío.

# 15. INTROS Y CUOTAS

`Tipo: Informacion` → `info;` conservando todos los INTRO, su identificador visible o `Intro_N`, su etiqueta completa, indicaciones ENC y formato.

`Función técnica: Cuota` obliga a generar la variable de cuota exactamente una vez con su tipo normal, categorías completas y códigos ordenados. `Regla de cuota` no autoriza inventar propiedades MDD: se conserva como dependencia funcional downstream y su asignación se implementará en etapa 4. Verifica que cada variable fuente mencionada exista en el Markdown; si no existe, bloquea QA en vez de omitir la cuota.

# 16. VARIABLES ADMINISTRATIVAS OBLIGATORIAS

Al final, antes de `End Metadata`, garantiza estos identificadores reservados en este orden:
- `INICIO`
- `INFO_INTRO_1`
- `ELIMI`
- `GRACIAS_ELIMI`
- `INFO_LINK`

Si el Markdown ya contiene uno de esos identificadores:
- si es semántica y técnicamente compatible, reutiliza una sola declaración;
- si entra en conflicto, NO renombres silenciosamente `ELIMI`, `ID_BASE` o `LINK`; detén QA y reporta colisión crítica.

# 17. SHELL/SYSTEM

No excluyas una declaración Shell válida si proviene de la base Shell técnica autorizada.
No inventes Shell si no existe dicha base.
No transformes variables del estudio en Shell.

La etapa 4 debe poder distinguir claramente:
- variables de estudio;
- administrativas reservadas;
- Shell/System.

# 18. FORMATO MDD

- Comienza exactamente con `Metadata(es-PE, Question, Label)` salvo que una base técnica autorizada defina otro locale explícito para el mismo estudio.
- Cuatro espacios por nivel.
- Una declaración lógica por línea.
- No Markdown/HTML/comentarios estructurales. Se exceptúan los marcadores `**...**` y `<u>...</u>` conservados literalmente dentro de cadenas de etiqueta entre comillas.
- No tabulaciones.
- Llaves, paréntesis, comillas, comas y `;` balanceados.
- Variables simples terminan en `;`.
- Categóricas terminan en `};` o `} atributo;`.
- `block fields` termina en `);`.
- loop termina exactamente en `) expand grid;`.
- Finaliza exactamente `End Metadata`.

# 19. QA DE SALIDA — GATE E2→E3

## 19.1 Cobertura
- Cada variable/subcampo del Markdown fue convertida o existe una razón explícita de exclusión técnica.
- Todos los intros y cuotas documentales fueron conservados.
- Ninguna variable proveniente de imagen, tabla, cuadro o forma que esté presente en el Markdown desapareció en MDD.
- Todas las variables administrativas reservadas existen una sola vez.

## 19.2 Identificadores
- Normalización determinista aplicada.
- Sin colisiones no resueltas.
- Ningún ID fue construido a partir de la etiqueta completa con espacios sustituidos por `_`.
- `ELIMI`, `ID_BASE` y `LINK` conservan sus nombres reservados.

## 19.3 Categorías
- Toda respuesta tiene identificador MDD.
- Toda respuesta capturable tiene `value`.
- Código, value y etiqueta siguen asociados correctamente.
- Las categorías están ordenadas por código conforme a la sección 11, tanto en variables como en listas.
- No existe ninguna categoría con etiqueta vacía no definida explícitamente.
- `other(...)`, `fix`, `exclusive` y orden no se duplican ni contradicen.
- Ninguna opción Otro tiene `other(...)` sin evidencia explícita de especificación/captura.

## 19.4 Estructuras
- Cada padre contiene sus subcampos.
- No se perdió una tabla de índices.
- Todos los loops terminan con `) expand grid;`.
- Ningún atributo numerado de una batería fue generado como pregunta principal independiente.
- Cada grid conserva padre, iteraciones, campos y escala sin aplanamiento.

## 19.5 Listas y formatos
- Cada conjunto o escala exactamente repetido dos o más veces utiliza una sola lista reutilizable.
- No existen listas duplicadas equivalentes.
- Negritas, subrayados, textos entre paréntesis e indicaciones ENC permanecen en las cadenas de etiqueta.

## 19.6 Sintaxis
- `Metadata(...)` y `End Metadata` presentes.
- Sintaxis balanceada.
- No hay Markdown ni comentarios.

## 19.7 Dependencias downstream
- Si existe base Shell, las variables Shell necesarias quedaron preservadas literalmente.
- Si no existe, no se inventaron y esa limitación queda como condición conocida para etapa 4.
- Cada cuota conserva una variable MDD real y una correspondencia verificable con su definición funcional de etapa 1.

Corrige y repite QA hasta no detectar errores corregibles. No entregues un MDD truncado o sintácticamente inconsistente.

# 20. SALIDA FINAL

Genera exactamente:
`[BASE_ESTUDIO].mdd.txt`

El archivo contiene únicamente MDD desde `Metadata(...)` hasta `End Metadata`.
