# 6. NORMALIZACIÓN DETERMINISTA
## 6.1 Identificadores
Normaliza cada identificador en este orden:
1. Conserva letras, números y guion bajo.
2. Reemplaza cada punto por `_`.
3. Reemplaza espacios y cualquier otro carácter no permitido por `_`.
4. Reduce guiones bajos consecutivos a uno.
5. Elimina guiones bajos iniciales y finales, salvo que el identificador fuente comience legítimamente con `_`.
6. Si comienza con un número, antepón `_`.
7. Conserva las mayúsculas y minúsculas del identificador fuente.

No sustituyas identificadores por sinónimos ni agregues prefijos no documentados.

## 6.2 Ubicación y orden de variables
- Conserva el orden documental de las variables principales.
- Mantén los subcampos inmediatamente dentro de su padre.
- Ubica las listas `define` inmediatamente antes de su primer uso.
- Si varias listas se usan por primera vez en el mismo punto, ordénalas por el orden de aparición de su conjunto base en el `.md`.
- Ubica las variables técnicas autorizadas de la sección 16 en la posición definida por la plantilla del proyecto; no las desplaces al final por defecto.

## 6.3 Nomenclatura de elementos técnicos
- Categoría con código explícito: `_CODIGO`.
- Categoría sin código: identificador posicional `_1`, `_2`, etc.
- Campo abierto asociado: `_C_CODIGO` o `_C_POSICION`.
- No generes `__Cod`, `_C__Cod` ni duplicaciones de guion bajo producidas por normalización. La forma técnica debe contener un solo separador `_` entre componentes, salvo que el identificador fuente explícito demuestre otra cosa.
- Campo común interior de loop sin identificador explícito: `Rp`.
- Lista reutilizable sin nombre explícito: `l_` seguido del identificador normalizado de la primera variable que la usa.

## 6.4 Igualdad
Dos conjuntos de categorías son iguales solo si, después de normalizar el marcado pero antes de reordenar, coinciden exactamente en cantidad, código asociado, wording visible, tipo de captura asociada, cardinalidad y atributos especiales. Las diferencias de espacios repetidos o marcado Markdown/HTML no rompen la igualdad; cualquier otra diferencia sí.

## 6.5 Colisiones
- Si dos variables o subcampos producen el mismo nombre normalizado, conserva el primero y añade `_2`, `_3`, etc. a los siguientes según el orden documental.
- Si se repite un código con etiquetas diferentes dentro de una misma lista, conserva el mismo `[value = CODIGO]` y añade `_2`, `_3`, etc. solo al identificador técnico de las apariciones posteriores.
- Si una categoría se repite exactamente por un artefacto de formato, consérvala una sola vez.
- Si colisionan nombres de listas, aplica el mismo sufijo incremental.

# 7. ETIQUETAS Y COMILLAS
Construye la etiqueta de variable así:
- Usa la etiqueta del `.md`.
- Para `PLATAFORMA_DESTINO = IFIELD`, no antepongas automáticamente `IDENTIFICADOR. ` al wording; iField puede mostrar el número a partir del nombre de variable.
- Para `PLATAFORMA_DESTINO = DIMENSIONS_ONLINE`, conserva el comportamiento anterior de anteponer `IDENTIFICADOR. ` cuando el identificador sea explícito y la etiqueta no lo contenga ya, salvo que la plantilla del proyecto indique otra cosa.
- Si no hay etiqueta, usa `""` únicamente cuando el `.md` realmente carezca de wording; no conviertas un error de extracción en etiqueta vacía.
- Conserva signos, acentos, mayúsculas, wording, errores y contenido visible.
- Conserva saltos de línea y énfasis relevantes mediante el marcado MDD/HTML compatible con el entorno cuando procedan del Markdown; no aplastes una separación intencional entre wording e instrucción.
- No traduzcas, completes ni corrijas el contenido sustantivo.
- Las instrucciones operativas del entrevistador deben representarse preferentemente con `_Osm_HiddenComment` cuando la Base Conceptual y el caso aplicable lo sustenten; no deben perderse ni mezclarse con lógica dinámica.

Para toda cadena MDD:
- abre y cierra siempre con comillas dobles;
- representa una comilla doble interna como `""`;
- conserva saltos intencionales con el mecanismo de presentación compatible cuando sean relevantes;
- reduce únicamente espacios consecutivos accidentales sin alterar contenido significativo;
- verifica que ninguna cadena quede con comillas abiertas o desbalanceadas.

La etiqueta `No precisa` debe escribirse exactamente como aparezca en el `.md`, dentro de comillas correctas. Ejemplo válido:
`_99 "No precisa" [value = 99] fix exclusive`

# 8. MAPEO ÚNICO DE TIPOS, CARDINALIDADES Y ESTRUCTURAS
Aplica todas las conversiones de tipo exclusivamente desde esta sección.

## 8.1 Categórica de respuesta única o RU
`categorical [1..1]`

## 8.2 Categórica de respuesta múltiple o RM
Conserva la cardinalidad explícita:
- RM sin límites explícitos: `categorical [1..]`
- RM con máximo 3: `categorical [1..3]`
- RM con mínimo 2: `categorical [2..]`
- RM con mínimo 2 y máximo 5: `categorical [2..5]`

Usa mínimo cero únicamente cuando el `.md` indique de forma expresa que la variable puede quedar sin respuesta. No suprimas ni inventes cardinalidades.

## 8.3 Texto
- Texto abierto general: `text [0..200];`
- Texto con longitud explícita: `text [MIN..MAX];` o la forma exacta autorizada por el `.md`.
- Tipo fuente `Otro` sin mapeo adicional: `text [0..200];`

## 8.4 Numérico entero
- Con rango explícito inequívoco: `long [MIN .. MAX] precision(10);`
- Sin rango explícito: `long [-2147483648 .. 2147483647] precision(10);`
- Conteo no negativo explícito: `long [0 .. 2147483647] precision(10);`

## 8.5 Decimal o monto
`double [0 .. 2147483647] precision(10);`, salvo que el `.md` indique literalmente otro rango permitido.

## 8.6 Fecha
`date;`

## 8.7 Información
`info;`

## 8.8 Tipo desconocido
Si el tipo no pertenece a los tipos definidos y no puede mapearse inequívocamente, usa `text [0..200];`.

## 8.9 Grid con varias variables
- Si todos los subcampos tienen el mismo tipo, cardinalidad y conjunto de categorías según la regla de igualdad, genera `loop ... fields - (...)` y selecciona la variante de grid según evidencia del `.md`, Base Conceptual y caso compatible; no impongas `expand grid`.
- Si los subcampos tienen tipos, cardinalidades o categorías diferentes, genera `block fields (...);`.
- Si no puede determinarse inequívocamente la homogeneidad, genera `block fields (...);`.

### 8.9.1 Grid con un subcampo y tabla adicional de índices

Cuando una variable esté declarada como `GRID con varias variables`, tenga un solo
subcampo y contenga dos tablas de categorías, no debe convertirse automáticamente
en una variable categórica simple.

Interpreta las tablas de acuerdo con su función estructural:

1. La tabla ubicada inmediatamente después de la definición del subcampo representa
   las categorías capturables del campo interno `Rp`.

2. La tabla adicional ubicada después de las categorías del subcampo representa las
   filas, atributos o índices del loop cuando:
   - sus elementos coincidan con atributos, marcas, productos, momentos, conceptos
     u objetos que deben evaluarse uno por uno;
   - la etiqueta o las indicaciones incluyan expresiones como `UNO POR UNO`,
     `UNA POR UNA`, `PARA CADA ATRIBUTO`, `PARA CADA MARCA`,
     `MOSTRAR UNA PANTALLA PARA CADA`, `EVALUAR CADA` o expresiones equivalentes;
   - la primera tabla sea claramente una escala de respuesta y la segunda tabla
     contenga los elementos que serán evaluados con esa escala.

En este caso, genera obligatoriamente:

PADRE "ETIQUETA COMPLETA DEL PADRE" loop
{
    FILAS O ÍNDICES TOMADOS DE LA SEGUNDA TABLA
} fields -
(
    Rp "ETIQUETA DEL SUBCAMPO"
    TIPO Y CARDINALIDAD DEL SUBCAMPO
    {
        CATEGORÍAS CAPTURABLES TOMADAS DE LA PRIMERA TABLA
    };
) GRID_VARIANT;

Donde `GRID_VARIANT` debe sustituirse por la variante corroborada (`grid`, `expand grid`, `column grid`, `column expand grid`, etc.). No uses `expand grid` por defecto.

No reemplaces la etiqueta del padre por la etiqueta del subcampo.

No conviertas esta estructura en una variable categórica simple.

No descartes la segunda tabla por estar precedida por otro encabezado genérico
`##### Categorías:`.

La presencia de un solo subcampo no impide generar un loop. En este patrón,
el número de niveles del loop está determinado por la tabla de índices, no por
la cantidad de subcampos declarados.

Si existen dos tablas, pero no puede determinarse inequívocamente cuál corresponde
a la escala y cuál a los índices, conserva la estructura como `block fields` y
no descartes ninguna tabla.


# 9. CATEGORÍAS, CÓDIGOS Y SINTAXIS CANÓNICA
## 9.1 Asociación entre wording y código
Separa siempre:
1. wording visible completo;
2. números o identificadores visibles dentro del wording;
3. código de respuesta explícitamente asociado;
4. fuente textual o estructural que confirma la asociación.

Conserva literalmente el wording, incluidos los textos o números visibles entre paréntesis. Obtén el identificador técnico y `value` del código explícitamente asociado, nunca de un número que forme parte únicamente del wording.

## 9.1.1 Categorías vacías

No generes una categoría adicional con código o `value` pero etiqueta vacía cuando no exista una alternativa real en el `.md`. Filas vacías, separadores de tabla, celdas de relleno y artefactos de maquetación no son categorías.

Si el `.md` presenta código y etiqueta inequívocos, conserva ambos. Si solo existe una celda vacía sin contenido de respuesta, omítela.

## 9.2 Generación de value
Toda categoría capturable debe incluir `value`, incluidas las filas o índices de loops y las categorías capturables del campo `Rp`.

- Con código explícito: `_CODIGO "ETIQUETA" [value = CODIGO]`.
- Sin código explícito: asigna `_1`, `_2`, etc. y `[value = 1]`, `[value = 2]`, etc. según el orden documental original.
- Conserva ceros iniciales en la lectura del identificador cuando sean parte del código visible, pero usa el valor numérico equivalente en `value` si el código es estrictamente numérico.
- Si la etiqueta está vacía, usa el código visible como etiqueta.

## 9.3 Orden numérico
Reordena las categorías por su código numérico ascendente, aunque el `.md` las presente en otro orden. Las categorías sin código se colocan después de las categorías con código y mantienen entre sí su orden documental posicional.

Si los códigos no son numéricos, ordénalos por su representación técnica normalizada en orden lexicográfico ascendente. Si existe una mezcla de códigos numéricos y no numéricos, coloca primero los numéricos y después los no numéricos.

Las posiciones fijas y las categorías especiales se reubican conforme a la sección 10 después de aplicar el orden numérico base.

## 9.4 Sintaxis canónica de cada alternativa
Usa siempre este orden:
`IDENTIFICADOR "ETIQUETA" [value = VALOR] other(...) ATRIBUTOS_ESPECIALES`

Reglas:
- `value` aparece primero.
- `other(...)`, cuando corresponda, aparece inmediatamente después de `value`.
- `fix`, `exclusive`, `fix exclusive` u otros atributos especiales aparecen al final.
- Nunca escribas atributos antes de `value` ni dentro de `other(...)`.
- Separa categorías con coma, excepto la última.

# 10. PRECEDENCIA Y RESPUESTAS ESPECIALES
Aplica en todos los casos este orden de precedencia, de mayor a menor:
1. exclusividad explícita indicada en el `.md`;
2. etiqueta especial inequívoca;
3. código técnico;
4. posición fija derivada de rotación u orden.

Una regla de mayor precedencia reemplaza cualquier atributo incompatible de menor precedencia. Los atributos compatibles se conservan en la sintaxis canónica.

## 10.1 Etiquetas especiales
Etiquetas como `Ninguno`, `No sabe`, `No responde`, `No precisa`, `NP`, `NS`, `NR` o `No aplica` **no reciben automáticamente** `fix exclusive`.

Aplica `fix`, `exclusive` o `fix exclusive` cuando:
- el `.md` lo marque explícitamente;
- la regla de rotación indique que la alternativa debe quedar fija;
- la Base Conceptual y un caso del mismo patrón confirmen el comportamiento para ese estudio/plantilla.

No conviertas una convención frecuente en regla universal.

## 10.2 Códigos técnicos
- Los códigos `94`, `96`, `98`, `99`, `89`, `90` u otros no tienen semántica universal.
- Conserva el código y determina `fix`/`exclusive` por wording, indicación explícita y evidencia del caso actual.
- No escribas `fix fix exclusive` ni dupliques atributos.

## 10.3 Exclusividad expresa

Las propiedades `exclusive`, `fix` y `fix exclusive` pueden aplicarse a categorías de cualquier pregunta categórica, incluido el field interno de un loop/grid; no las restrinjas a preguntas múltiples.
Si el `.md` marca una alternativa como exclusiva, aplica `exclusive`. Si además debe quedar fija por una regla compatible, usa `fix exclusive`.

## 10.4 Posición fija
Las opciones fuera del universo de rotación reciben `fix`, salvo que ya les corresponda `fix exclusive` por una regla de mayor precedencia.

# 11. OTHER, CAPTURAS ASOCIADAS Y ROTACIÓN
## 11.1 Generación de other(...)
Genera `other(...)` solo cuando el `.md`:
- solicite inequívocamente especificar;
- muestre una línea o campo abierto asociado;
- identifique inequívocamente una captura textual o numérica asociada.

La palabra `Otro`, `Otra` u `Otros` por sí sola no autoriza `other(...)`.

Ejemplos canónicos:
`_94 "Otro" [value = 94] other(_C_94 "" text [0..200]) fix`
`_1 "Edad exacta" [value = 1] other(_C_1 "" long [18 .. 99] precision(10))`

No generes variables auxiliares separadas para una captura asociada, salvo que el `.md` la declare como variable independiente.

## 11.2 Rotación y orden
Convierte únicamente instrucciones explícitas:
- ROTAR o ROTANDO → `rot`
- RANDOMIZAR, ALEATORIZAR o ALEATORIAMENTE → `ran`
- ALFABÉTICO A-Z → `asc`
- ALFABÉTICO Z-A → `desc`
- INVERTIDO → `rev`

En pregunta simple, coloca el atributo después de cerrar las categorías: `} rot;`, `} ran;`, `} asc;`, `} desc;` o `} rev;`.

En loop, colócalo después de cerrar las filas y antes de `fields -`: `} rot fields -`, `} ran fields -`, `} asc fields -`, `} desc fields -` o `} rev fields -`.

No muestres la instrucción de rotación como etiqueta o comentario. Mantén fuera del universo de rotación, con `fix` o `fix exclusive` según precedencia, las opciones que el `.md` excluya expresamente y las respuestas especiales.

# 12. LISTAS DEFINE
Crea una lista reutilizable cuando el mismo conjunto base de alternativas aparezca más de una vez o cuando el `.md` identifique una lista común.

No crees listas para conjuntos usados una sola vez, salvo instrucción expresa.

Las listas reutilizables contienen solo opciones base. Excluye de ellas opciones abiertas, respuestas especiales y exclusivos propios de una pregunta. Agrega esas alternativas directamente en cada variable, loop o `Rp`.

Toda categoría de una lista `define` debe incluir `value` y respetar el orden, la precedencia y la sintaxis canónica.

Antes de emitir variables repetitivas, compara todas las escalas. Si dos o más conjuntos base son idénticos según la regla de igualdad, reutiliza una sola lista `define/use` salvo que una diferencia funcional documentada requiera mantenerlos separados. Esta regla busca evitar duplicación y pérdida de escalas, no forzar listas para conjuntos parcialmente similares.

# 13. LOOPS Y BLOCK FIELDS
## 13.1 Loop homogéneo
Usa esta estructura:
`PADRE "ETIQUETA" loop`
`{`
`    _1 "ELEMENTO 1" [value = 1],`
`    _2 "ELEMENTO 2" [value = 2]`
`} fields -`
`(`
`    Rp ""`
`    TIPO_MDD`
`    {`
`        _1 "OPCIÓN 1" [value = 1],`
`        _2 "OPCIÓN 2" [value = 2]`
`    };`
`) expand grid;`

Reglas obligatorias:
- Las filas o índices del loop siempre incluyen `value`.
- Las categorías capturables de `Rp` siempre incluyen `value`.
- Usa el código explícito de cada fila si existe; de lo contrario, usa numeración posicional.
- Las filas se ordenan conforme a la sección 9 y las alternativas de `Rp` conforme a las secciones 9 y 10.
- Si el `.md` no aporta un identificador común interior, usa `Rp`.
- No fuerces `expand grid` en todos los loops. Selecciona `grid`, `expand grid`, `column grid`, `column expand grid` u otra variante únicamente cuando esté sustentada por el `.md`, la Base Conceptual y un caso técnicamente equivalente.
- `ran fields` significa aleatorización de filas/iteraciones; no lo confundas con `ran` aplicado a categorías.
- Si no existe evidencia para un modificador exclusivamente visual, usa la forma mínima compatible con la estructura lógica y evita inventar propiedades de presentación.

## 13.2 Block fields heterogéneo
Usa esta estructura:
`PADRE "ETIQUETA" block fields`
`(`
`    SUBCAMPO1 "ETIQUETA"`
`    TIPO;`
`    SUBCAMPO2 "ETIQUETA"`
`    TIPO;`
`);`

Conserva el orden documental de los subcampos, normaliza sus identificadores y no añadas `expand grid`.

## 13.3 MaxDiff

Cuando `Función técnica: MaxDiff` esté documentada:

- busca primero un caso MaxDiff corroborado en las bases;
- conserva el conjunto de atributos y las dimensiones de elección como una única estructura;
- usa el patrón de loop/grid correspondiente al caso compatible, por ejemplo columnas `MÁS IMPORTANTE` / `MENOS IMPORTANTE`;
- reutiliza la lista de atributos mediante `define/use` cuando corresponda;
- asocia `_Osm_CustomFunction = "validaMaxDiff"` únicamente cuando esa función forme parte del estándar/caso autorizado para la etapa lógica;
- no generes atributos, sets ni combinaciones que no estén documentados.

## 13.4 Cuotas

Cuando `Función técnica: Cuota` esté documentada:

- conserva la variable de cuota como entidad separada de la variable fuente;

# 14. RANGOS, VALIDACIONES Y LÓGICA OPERATIVA
## 14.1 Rangos
Reconoce rangos solo cuando sean explícitos e inequívocos, por ejemplo `RANGO DE 0 A 60` o `PERMITIR RANGOS DE 1946 A 2007`. Extrae literalmente mínimo y máximo.

## 14.2 Validaciones
Genera `validation(...)` únicamente cuando el `.md` contenga una expresión regular literal o una especificación exacta cuya traducción esté definida expresamente en este prompt.

No inventes expresiones regulares para teléfono, correo, moneda, separadores de miles ni fechas. Una indicación como `USAR SEPARADOR DE MILES CON PUNTO` no autoriza por sí sola una validación inventada.

## 14.3 Lógica operativa
No incorpores indicaciones como `MOSTRAR`, `HABILITAR`, `TERMINAR`, `CONTINUAR`, `APAGAR AUDIO`, saltos o filtros. Solo pueden afectar la salida si determinan un rango o validación autorizados, o si son una instrucción de rotación contemplada en la sección 11.

# 17. CASOS AMBIGUOS Y PROHIBICIONES
## 17.1 Resolución determinista
1. Si falta etiqueta, usa `""`.
2. Si falta código, usa numeración posicional según el orden documental original y luego aplica el orden definido.
3. Si el tipo es desconocido, usa `text [0..200];`.
4. Si un rango es ambiguo, usa el rango general.
5. Si un grid no puede clasificarse como homogéneo, usa `block fields`.
6. Si la captura asociada no es inequívoca, no generes `other(...)`.
7. Aplica siempre la precedencia: exclusividad explícita → etiqueta especial → código técnico → posición fija.
8. No tomes decisiones aleatorias.

## 17.2 Prohibiciones
Está prohibido:
- inventar variables, etiquetas, categorías, códigos, rangos o validaciones;
- omitir variables técnicas autorizadas y necesarias para el estudio;
- incorporar contenido de archivos distintos del `.md`;
- cambiar códigos explícitos;
- completar textos truncados;
- traducir o corregir contenido sustantivo;
- deducir lógica no documentada;
- crear bloques o auxiliares no respaldados;
- omitir `value` en categorías capturables, filas de loop o categorías de `Rp`;
- generar `other(...)` sin solicitud inequívoca o captura asociada;
- incumplir el orden canónico `value` → `other(...)` → atributos;
- aplicar o retirar `fix`/`exclusive` por semántica universal de un código; cada atributo debe estar sustentado por el `.md` o un caso autorizado;
- forzar `) expand grid;` en un loop cuyo caso requiera otra variante de grid;
- generar más de un archivo de salida.
